## 2. The real pipeline, traced end to end

`POST /api/chat/message` → `ChatService.processMessage()` (`chat.service.ts:124`):

```
governance gate (advisory-only, see §3.7)
  → IntentClassifierService.classify()
  → MoERouterService.createRoutePlan()          [real expert selection]
  → ContextBuilderService.buildContextPacket()   [real context assembly]
  → RoutingOptimizerService.optimizeRequest()    [SECOND, independent model choice]
  → memory fetch (short/long/clinical, parallel) [real, UUID-gated]
  → RAG retrieval + aiService.invokeLLMWithTools() [real LLM call]
  → toolOrchestrator.executeInChat()             [real, first-tool-call-only]
  → ResponseComposerService.compose()
  → finalizeAssistantTurn():
       persistAssistantMemory()   [real]
       recordAssistantArtifact()  [real, gated on length/citations]
       recordEvaluationRun()      [was fabricated+uncategorized, now fixed]
```

This is genuinely more sophisticated than expected going in — most of the pipeline the request describes is real and wired. The findings below are about where it disagrees with itself, fabricates precision it doesn't have, or where a second, fake entry point undermines the real one.

## 3. Findings (not fixed this round — documented, prioritized)

### 3.1 CLOSED 2026-08-08 (ED Copilot AI-Runtime Convergence round) — a fake, HTTP-reachable copilot sat alongside the real one

`EDCopilotService.processQuery()` was reachable at two real routes and returned confident-sounding hardcoded text ("move patient" logic, canned chest-pain/sepsis/stroke advice, fixture patient data) with **zero LLM involvement** — a keyword `if/else` chain. A full call-graph trace confirmed both routes (`POST /api/emergency/copilot/query`, `POST /api/copilot/query`) have zero real frontend callers, so no consumer migration was needed — but the trace also found the real, live copilot path (`CopilotPanel.tsx` → `POST /api/ai/node/conversational` → `ChatService.processMessage()`) had **no** priority/DPS-change safety-floor check at all, a more severe gap than the duplicate-runtime finding itself: the 2026-08-06 fix (§ referenced by the Master Scorecard's Domain 12) had landed in the unreachable `EDCopilotService`, not the path real traffic uses. Fixed: the safety-floor check was ported into `ChatService.handleEdCopilotPriorityChange()` (checked first, fail-safe); a field-name mismatch was found and fixed (`CopilotPanel.tsx` sends `capacityBand`/`capacityScore`/`reassessmentQueueCount`, not `capacitySnapshot`/`flaggedReassessments`, so several dispatcher branches were silently inert on real traffic); a hardcoded `modelProvider: 'anthropic'` on every response (including deterministic ones) was fixed; a full `provenance` object was added to every ED-copilot response. Both HTTP routes now delegate to `ChatService.processMessage()` via a new `buildEdCopilotOperationalContext()` that assembles real patients/capacity/reassessment/patient-safety context from the controller's own injected services. `EDCopilotService.processQuery()` was deleted outright. Full writeup in the Master Scorecard's Domain 12. **No longer P0 — closed.**

### 3.2 DUPLICATE — four independent model/expert-selection systems, one is a fully dead 1,389-line duplicate

1. `MoERouterService` + `expert-selector.service.ts` — real, wired (`chat.service.ts:237`).
2. `RoutingOptimizerService` — real, wired, but **independently** re-picks a model (`lightweight_model`/`rag-mini`/`clinical-expert`) *after* MoE already chose an expert; nothing reconciles the two, both are stuffed into response metadata side by side.
3. `lib/native-ai/panelOfExpertsRouter.ts` — real, frontend-only, scores an entirely different catalog (`CLINICAL_DOMAIN_SPECIALISTS`); its routing decision never reaches the backend.
4. `backend/src/modules/ai/foundation/` (`ai-routing-engine.service.ts`, 376 lines; `ai-context-manager.service.ts`; `ai-response-composer.service.ts`; `ai-expert-descriptors.ts`, 349 lines) — **correcting an imprecise claim from this round's own investigation**: these ARE registered as real NestJS providers and exported from `AiModule` (`ai.module.ts:44-57`), not "never imported into any Nest module" as first reported. Verified directly: zero files anywhere outside `foundation/` itself, its own 3 spec files, and `ai.module.ts`'s registration reference them. Same bug shape as Round 44's `IncidentReportingService` — DI-registered, even exported for other modules to use, but no real caller ever injects and calls it. `AiRoutingEngineService.createRoutePlan()` — the exact same method name as `MoERouterService.createRoutePlan()` — strongly suggests this was an earlier or parallel implementation of the identical responsibility, abandoned in place rather than removed.

None of the 4 systems can currently produce a genuinely wrong *routing* decision that reaches a patient (only #1 and #2 are in the live path, and both execute — they just don't agree on which model to bill/log), but #3 and #4 are real, substantial, tested code that looks load-bearing and isn't. **P1**: #4 specifically needs the same careful "confirm zero consumers, confirm no unique capability would be lost" verification rounds 39-43 applied before removing anything this size (1,389 lines across 9 files) — not rushed into this round.

### 3.3 Memory — working, with a real functional cliff

`ChatService.buildAssistantMemoryContext()`/`persistAssistantMemory()` genuinely call the real `short`/`long`/`clinical` memory services in parallel and inject results into the model's context. But every read and write is skipped — silently, `{available: false, reason: 'non_uuid_user'}` — unless `userId` matches a UUID pattern (`chat.service.ts:797`, `:1074`). Whether real production users always have UUID ids (in which case this is dead-but-harmless defensive code) or sometimes don't (in which case it's a real, silent context-loss bug matching the request's own "context loss" concern) is unverified this round — checking the `User` entity's real id generation and every auth path that issues a `userId` is its own bounded piece of work. **P1, needs its own verification pass.**

### 3.4 UNWIRED — streaming is fully built and completely unused

`streamAI()`/`streamAIResponse()` in `lib/ai/client.ts` do real SSE parsing; only the Anthropic adapter actually supports `stream: true` (OpenAI/Azure/Groq/Gemini explicitly reject it). Zero components import the streaming functions. `POST /api/chat/message` always returns one complete response. An `AI_STREAMING_ENABLED` config flag exists and gates nothing in the real chat path. This is the same "built capability, zero consumers" shape this whole campaign keeps finding (Round 44's `IncidentReportingService`, Round 45's route-orphan-detector stub) — just in the UX layer this time, not governance. **P2**: real UX work (loading-state redesign), not a quick fix, and not attempted here.

### 3.5 Artifacts — real on the write side, dead on the read side

The copilot genuinely persists artifacts server-side (`recordAssistantArtifact()`, gated on having tool/citation/RAG context and ≥160 chars of text). `src/services/artifactsApi.ts` exports a working HTTP client for reading them back — but no page imports it; the only frontend consumer of "artifacts" is `LOCAL_ARTIFACTS`, static fixture data in `src/data/platformOperatingSystem.ts`. Real generated artifacts are currently unrecoverable through the UI. **P1**: needs a real `Artifacts` page or panel, a genuine feature build, not a wiring fix.

### 3.6 Truthfulness — `AdministrativeAutomationTask.aiGenerated: true` on rule-generated output

`administrative-automation-orchestration.lib.ts`'s `buildAdministrativeAutomationSnapshot()` produces tasks from deterministic rules over patient state (overdue vitals, wait thresholds, etc.) and marks every one `aiGenerated: true` (`:106`) regardless. This is the exact "heuristic defaults to live/AI" bug shape this campaign has fixed five separate times in Domain 12 (`nativeAiCore.ts`, `clinicalAcuityModel.ts`, `modelRegistry.ts`, twice more) — same shape, different file. **P0 for a future round** — narrow, well-precedented, safe fix (rename the field or correct its value), just not reached this round given time already spent on the higher-severity evaluation-metrics fix below.

### 3.7 Approvals — the gate that's supposed to block doesn't

`tool-orchestrator.service.ts:348`'s `evaluateGate()` runs but a real existing test (`PlatformGovernanceWorkspace.test.tsx:87`) explicitly asserts the gate is non-blocking at 3 of 4 call sites — advisory only. The copilot creates real governance review items, but no SPA page calls the review endpoints, so nothing ever acts on them. A second, separate, fully-working human-approval loop (`workflow-orchestration/review`, `approve|modify|override|dismiss`) exists but has no connection to anything the AI pipeline produces. **P1**: deciding whether the gate should become blocking is a product/safety decision, not a code-only fix — flagged, not guessed at.

### 3.8 Execution — real, with three specific, named limits

`toolOrchestrator.executeInChat()` genuinely shares the same `executeTool()` the calculator endpoints use — real, single execution path. Three concrete gaps: only the first LLM tool-call is executed ("Take the first tool call for MVP" — the code's own comment); execution failures are swallowed to `logger.warn` with no surfaced error; no approval step precedes execution regardless of the review-item system in §3.7. **P2**: each is a bounded, well-defined fix, none reached this round.

## 4. Fixed this round

### 4.1 The primary fix — fabricated per-turn metrics were silently counted as measured production quality

`ChatService.recordEvaluationRun()` called `EvaluationService.createRun()` with `hallucinationRate: citations.length > 0 ? 0.02 : 0.05` (a rule, not a measurement — no hallucination-detection ever ran) and `userSatisfaction: 4.5` (a hardcoded literal — no human ever rated anything). `EvaluationService` itself already has a carefully-built honesty system for exactly this risk — a `seedOnly` flag, a `measuredSource` field, and a `getDashboard().honesty` block that explicitly warns "Aggregates are SEED-ONLY demo values... Do not use for model promotion" when no real measured runs exist. But `CreateEvaluationRunDto` never exposed `seedOnly` as a settable field at all, and `createRun()` left it `undefined` on every run it constructed — which `getDashboard()`'s `!run.seedOnly` filter treats as **measured**. Every real copilot conversation was silently feeding fabricated numbers into the exact aggregate/trend/benchmark pool the honesty system exists to protect, with the `aggregateIsSeedOnly` flag reporting `false` even though nothing had actually been measured.

**Fix**: added `seedOnly?: boolean` to `CreateEvaluationRunDto`, defaulted `createRun()` to `seedOnly: dto.seedOnly ?? true` — safe-by-default, matching the same "don't trust the boundary until proven" principle used for the Workspace contract validation last round — so a caller must now explicitly assert `seedOnly: false` to have a run counted as measured. `ChatService`'s call now explicitly sets `seedOnly: true` (not just relying on the default, for clarity of intent) with an honest, field-specific `notes` string distinguishing the 4 fabricated metrics from the 3 real per-turn signals (`latencyMs`/`costUsd`/`toolExecutionSuccess`) the same run also carries.

**Verification**: 3 new tests in `evaluation.service.spec.ts` (defaults to `seedOnly: true`; a default-seedOnly run is excluded from the dashboard's measured pool; an explicit `seedOnly: false` run is included), the existing `rawScores` test updated to explicitly assert real-harness usage (`seedOnly: false`), and a new source-level test in `chat.assistant-integration.spec.ts` (matching this file's own established pattern) proving the exact call site sets `seedOnly: true`. All passing — see §6.

### 4.2 A real, separate, previously-latent build-config bug found while verifying the fix above

Running `cd backend && npm run build` after the fix above failed — not from the fix itself, but because `backend/tsconfig.build.json`'s `exclude` list has a known, already-worked-around quirk: general glob excludes like `**/*.test.ts` don't reliably apply across the config's own `../`-relative `include` entries (the file's own prior author already knew this — `../lib/**/*.test.ts` exists as a redundant, file-specific exclude alongside the general pattern for exactly this reason). `src/types/workspaceContracts.parity.test.ts` (added in the prior round) was silently being swept into the backend's compile graph and failing on `import.meta.url`, a frontend-only ESM construct. This means the backend build was one new `.test.ts` file away from breaking for anyone at any time — a real, if narrow, fragility. **Fix**: added `"../src/types/**/*.test.ts"` to the exclude list, mirroring the exact existing `../lib/**/*.test.ts` pattern. Verified: `nest build` clean afterward.
