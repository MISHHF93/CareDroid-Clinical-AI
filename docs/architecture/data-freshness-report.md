# Data Freshness Report

Date: 2026-06-14

## Scope

This pass traced active CareDroid Emergency OS data sources across the frontend and backend without changing the single AppShell, route system, navigation registry, API facade, Emergency OS domain model, operational state model, alert/escalation model, or design system.

Source classes used in this report:

- `FIXTURE`: deterministic static or generated demo data.
- `MOCK`: test-time mock or disabled capability substitute.
- `API`: REST facade or backend service envelope.
- `REALTIME`: WebSocket, SSE, subscription, or polling path intended to keep operational state current.
- `LOCAL_PERSISTED`: browser/device persistence such as `localStorage`.
- `DERIVED_STORE`: computed Zustand/store state derived from fixtures, API envelopes, or local actions.
- `MANUAL_REVIEW`: external clinical/operational data represented as placeholder, review queue, or disconnected connector.

## Active Freshness Model

Active Emergency OS pages use one of three freshness paths:

1. Route-level hooks in `src/hooks/useEmergencyOs.js` call the canonical facade in `src/services/emergencyOsApi.js`. If a scenario is active, `buildEmergencyScenarioModuleEnvelope()` wins before the API request and returns a `source`, `generatedAt`, and scenario label.
2. `src/store/emergencyStore.ts` initializes from `buildSrcEmergencyScenarioState()`, then `initializeFromBackend()`/`refreshAllData()` hydrate store slices from `/api/emergency/*` envelopes. Store actions update local operational state immediately.
3. `src/hooks/useCareDroidCentralNode.ts` starts `src/services/emergencyRealtimeService.js`, which uses configured SSE/WebSocket paths when present and otherwise polls the central-node snapshot. Header sync now shows the realtime mode and last sync age.

Backend Emergency OS envelopes are generated by `envelope()` in `backend/src/modules/emergency-os/emergency-os.services.ts` and `backend/src/modules/emergency-os/emergency-os.upgrade-harness.service.ts`. They consistently include `generatedAt` and `source: backend-fixture`, but the UI must keep that label visible so operators do not mistake fixture-backed data for live clinical integration.

## Fixes Applied

- Added a Header sync badge that shows the realtime mode and age from `centralSnapshot.sync` instead of only `Synced`/`Sync stale`.
- Preserved fleet snapshot `generatedAt` in `src/services/emergencyTransportApi.js`.
- Updated EMS Pipeline source copy to show the Emergency OS module source and freshness, plus fleet feed freshness.
- Updated Referral Panel source copy to show referral envelope source and freshness beside the existing specialty/transfer context.

## Remaining Manual-Review Risks

- `src/hooks/useEmergencyWebSocket.ts` should either be retired from active Emergency OS paths or expanded to write the same detailed websocket status model used by `emergencyRealtimeService.js`.
- Scenario mode should gain a global visible banner if pilots keep using persisted `caredroid.edScenarioId` across refreshes.
- EMS Unit Visibility should render per-unit `freshness`/GPS recency if `/api/fleet/snapshot` returns vehicle-level values.
- Local-first actions need a durable conflict policy before production use: queue, retry, server acknowledgment, and refresh reconciliation should be explicit per action.
- Provincial health, HL7, IoT vitals, EMS CAD/ePCR, wearable/BLE, and FHIR sources remain placeholders or demo feeds until credentials and ingestion contracts are connected.
