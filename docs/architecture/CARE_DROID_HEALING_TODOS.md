### Infrastructure note (2026-08-09) — the long-standing "`vitest` is blocked in this sandbox" constraint (cited by dozens of prior entries in this ledger, e.g. HEAL-008/HEAL-030) was a machine-level Windows Smart App Control policy, not a Claude Code sandbox limitation

The user disabled Smart App Control this session. **`vitest` now works and has been used for real validation for the first time in this campaign** (confirmed: `npx vitest run <file>` executes and reports real pass/fail, not a spawn error). This means the "vitest blocked, relied on typecheck + direct source tracing" caveat on every prior VALIDATED entry no longer reflects current environment capability — future rounds should prefer real `vitest run` validation over the manual-hand-verification fallback where the environment allows it, though this may be session/machine-specific (Smart App Control could be re-enabled) so this note documents the finding rather than assuming it is permanent.

**First real dividend**: a full frontend `npm run test:run:stable` pass (969 test files, never previously run end-to-end in this campaign; completed once — 15 files/20 tests failed out of 12,338 tests) surfaced 13 genuine findings, 11 fixed and `VALIDATED` this round (HEAL-034, HEAL-036, HEAL-037 through HEAL-043 below), 1 real gap surfaced-but-deferred (HEAL-039's Training/AI-Evaluation RBAC-gating follow-up), and 2 left open for a future round: HEAL-044 (`R12EndToEndWiring.test.tsx`'s capacity-badge finding — genuinely ambiguous, needs investigation) and `src/test/pilotWalkthrough.test.tsx` (fails with a React `act()`-wrapping warning at `PatientDetailPanel`, 53s runtime — not yet triaged as a real bug vs. test-harness noise). ### HEAL-037 — `WorkspaceContext.tsx`'s `switchWorkspace()` silently left `activeWorkspace` pointing at the PREVIOUS workspace's data (assistantContext/shortcuts/toolIds/workspaceProfile/etc.) when switching to a workspace that exists only in the local `CARE_WORKSPACES` registry but not in the backend's per-user workspace membership list

- **Severity**: P1_HIGH (real state-leak bug — matches the operating directive's explicit "local state diverging from backend truth" category; every consumer of `useWorkspace()` reading `assistantContext`/`shortcuts`/`workspaceProfile`/`defaultDashboardWidgets`/`defaultFilters`/`restrictedAssets`/`recommendedAIAgents`/`recommendedAssetPacks` would silently keep showing the OLD workspace's values after a switch, with `activeWorkspaceId` correctly reporting the new one — a genuine split between what the UI's id-state says and what its data-state actually reflects)
- **Domain**: Operational state architecture — first real bug found via this session's newly-unblocked `vitest run` (see infrastructure note above); previously undetectable because this test file could never execute
- **Source evidence**: `npx vitest run src/test/WorkspaceContext.backend.test.tsx` failed: `does not leak stale backend context after switching to a local workspace` — after `switchWorkspace('emergency')`, `assistantContext` remained `'ICU assistant context'` (the previous workspace's value) instead of resetting. Traced root cause in `src/contexts/WorkspaceContext.tsx`: (1) `applyBackendContext()`'s `workspaces` state is built from `mergeWorkspacesWithRegistry(normalizedWorkspaces, defaultWorkspaces())` (`sidebarToolPresentation.ts:78-98`), which only `.map()`s over the backend-provided `normalizedWorkspaces` list to enrich `toolIds` — it never appends entries from `defaults` that are absent from the backend list, so `workspaces` state can legitimately contain fewer entries than the full local `CARE_WORKSPACES` registry (e.g. exactly 1, if the backend's per-user workspace-membership response only includes 1 workspace). (2) `switchWorkspace(workspaceId)`'s own `if (!target)` branch (lines 288-292, pre-fix) is explicitly designed to handle switching to such a local-only workspace id — it correctly updates `activeWorkspaceId` and clears `workspaceContext` — but never adds a corresponding entry to `workspaces` state. (3) `activeWorkspace = workspaces.find((w) => w.id === activeWorkspaceId) || workspaces[0] || null` (line 326-327 original) then silently falls back to `workspaces[0]` — an arbitrary (in practice, the previously-active) entry — because the real target was never added to `workspaces`. (4) Every field in the exposed context `value` (`assistantContext`, `shortcuts`, `workspaceProfile`, `defaultDashboardWidgets`, `defaultFilters`, `restrictedAssets`, `recommendedAIAgents`, `recommendedAssetPacks`) reads `activeWorkspaceContext?.workspace?.X || activeWorkspace?.X || fallback`, so once `activeWorkspace` resolved to the wrong object, all of these silently leaked the stale workspace's data. Confirmed `'emergency'` (the test's switch target) is a real entry in the local registry (`src/data/workspaceArchitecture.ts:357`, `id: 'emergency'`), and `getActiveWorkspaceState()`/`listForUser()` (`backend/src/modules/workspaces/workspaces.service.ts:90-96`) genuinely return only the workspaces a user has an active `WorkspaceMembership` row for — so a user with fewer backend-provisioned workspace memberships than the full local registry (a realistic, not hypothetical, tenant configuration) can hit this exact path in production, not just in the test's mock.
- **Affected files**: `src/contexts/WorkspaceContext.tsx` (`switchWorkspace()`'s `!target` branch now looks up the requested id in `defaultWorkspaces(clientProfile, user?.role)` and adds it to `workspaces` state if found and not already present, before returning; dependency array extended with `clientProfile`/`user?.role`)
- **Runtime impact**: Real — a user switching to a locally-registered-but-not-backend-provisioned workspace now sees that workspace's own assistant context/shortcuts/tool defaults instead of silently retaining the previous workspace's.
- **Frontend impact**: Every `useWorkspace()` consumer (sidebar tool presentation, AI assistant context injection, dashboard widget defaults, asset restrictions) now reflects the actually-active workspace after such a switch.
- **Backend impact**: None (frontend-only fix; the backend's per-user membership scoping behavior is correct and unchanged — the frontend needed to handle its own documented local-fallback case correctly).
- **AI/ML impact**: `assistantContext` (injected into AI Copilot prompts per-workspace, per this file's own naming/usage) was one of the leaking fields — this fix prevents a stale prior workspace's assistant framing from silently persisting into a new workspace's AI interactions.
- **Affected user profiles**: Any profile using multi-workspace switching where local (CARE_WORKSPACES-registry) workspaces outnumber a given user's real backend workspace memberships — plausible for Department Manager/Site Admin profiles configuring/exploring workspace types not yet backend-provisioned for their organization.
- **Security/privacy impact**: None (no cross-tenant data exposure — the leaked data was the same user's own previous-workspace configuration, not another user's or tenant's).
- **Clinical-safety impact**: Indirect — a stale `assistantContext`/`restrictedAssets`/`defaultFilters` bleeding into a new workspace could present a clinician with tool defaults or AI framing scoped to the wrong care context (e.g. ICU assistant framing while nominally in the Emergency workspace).
- **Current status**: `VALIDATED`
- **Dependencies**: None.
- **Recommended canonical solution**: Applied. A more thorough future fix could make `mergeWorkspacesWithRegistry` eagerly include all local-registry workspaces up front (not just enrich existing ones), which would make this particular lazy add-on-switch patch unnecessary — left as a possible follow-up, not required to close this bug.
- **Validation requirements**: `npx vitest run src/test/WorkspaceContext.backend.test.tsx src/test/WorkspaceContext.test.tsx` — 2/2 files, 25/25 tests passing. `npx vitest run` on 4 other real `useWorkspace()` consumer test files (`OrganizationIntelligenceProfile.test.tsx`, `ProfileToolPreferences.test.tsx`, `ToolsOverview.inventory.test.tsx`, `ToolsOverview.visibility.test.tsx`) — 4/4 files, 33/33 tests passing, zero regressions. Full frontend `npx tsc --noEmit -p tsconfig.frontend.json` clean.
