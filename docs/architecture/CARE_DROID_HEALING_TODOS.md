### HEAL-076 (P1_HIGH, VALIDATED) — the SSE realtime stream (the ONLY transport EventSource clients can use) unconditionally 403'd on every connection, for every user, always — real-time whiteboard/alert/collaboration updates have been silently non-functional

- **Severity**: P1_HIGH (not cosmetic — every live-push update path in the app depended on this connection; a page relying on it for real-time data would only ever see its own initial fetch, never a push update, with the failure silently swallowed by `apiClient.ts`'s dev-mode 401/403 suppression, matching the exact silencing pattern HEAL-071 already documented for a different auth gap)
- **Domain**: Real-time/event architecture (MB-H6, new — continues Area H's event-publisher scope; found while investigating `/emergency/settings`'s known slow-settling behavior per MB-E13's page-sweep continuation)
- **Source evidence**: live Playwright network trace of `/emergency/settings` showed `GET /api/emergency/realtime/stream?token=...` returning 403. Reproduced directly via `curl` against the raw backend (bypassing the browser entirely, ruling out any frontend-side confound) with a real, well-formed, unexpired dev JWT: `{"success":false,"error":{"code":"FORBIDDEN","message":"Authenticated user is required for tenant context.",...}}`. Traced the message to `TenantContextService.resolveForRequest`'s very first line: `if (!user?.id) throw new ForbiddenException(...)`. `EmergencyRealtimeController.stream()` (and its sibling `CollaborationRealtimeController.stream()`, whose own comment says it's "guarded like emergency/realtime") declare only `@UseGuards(JwtQueryAuthGuard)` — a custom guard that exists specifically because `EventSource` cannot set an `Authorization` header, so it verifies the JWT directly from a `?token=` query param instead of going through Passport. It sets `request.user = payload` — the RAW decoded JWT claims, which carry `sub` (the standard JWT subject claim; confirmed via `auth.service.ts`'s own token-signing code, which never emits an `id` field, only `sub`), never `id`. Separately, `TenantIsolationGuard` AND `TenantContextInterceptor` are registered **globally** via `APP_GUARD`/`APP_INTERCEPTOR` in `tenant-context.module.ts` (a `@Global()` module) — meaning they run on **every** route in the app regardless of that route's own `@UseGuards()` list, a fact the route-level guard declaration alone doesn't reveal. Both call `resolveForRequest(request.user, ...)`, which requires `user.id` — present on every OTHER authenticated path (the normal `AuthGuard('jwt')` → Passport's `JwtStrategy.validate()` looks up the real `User` row by `payload.sub` and returns the full, `id`-bearing entity) but absent here. Found a strong secondary signal pointing at the same root cause: `CollaborationRealtimeController.stream()`'s own handler body already reads `req.user?.sub || req.user?.id || ''` — a defensive fallback for exactly this `.sub`-vs-`.id` mismatch, added at the point of use, which can never actually help because the global guard/interceptor pair rejects the request with a 403 before that handler body ever runs. This is a systemic bug (every user, every environment), not an artifact of the dev-bypass session used to discover it — confirmed by reading the JWT-signing code directly rather than assuming.
- **Fix**: `JwtQueryAuthGuard.canActivate()` now sets `request.user = { ...payload, id: payload.sub }` instead of the raw payload, mapping the JWT's `sub` claim to the `id` field every other guard/service in the tenant-context chain expects — a minimal, additive, single-line-of-intent fix at the actual point of divergence (the guard that populates `request.user` for this one non-Passport auth path) rather than patching every downstream consumer with `.sub || .id` fallbacks that can't work anyway given the global guard ordering.
- **Affected files**: `backend/src/modules/emergency-os/guards/jwt-query-auth.guard.ts`, `backend/src/modules/emergency-os/guards/jwt-query-auth.guard.spec.ts` (new — this guard had zero test coverage before this round, which is why the bug was never caught)
- **Validation**: `npx tsc --noEmit -p tsconfig.json` (backend) clean. `npx eslint` clean on both files. New `jwt-query-auth.guard.spec.ts` (5/5: id-mapping from query-string token, id-mapping from Authorization header, missing-token rejection, wrong-tokenUse rejection, verification-failure rejection). Full `tenant-context`/`emergency-realtime`/`collaboration-realtime` blast radius (8 suites, 24 tests) green, 0 regressions. **Verified live end-to-end**: rebuilt the backend, restarted it, re-curled the exact same request that previously 403'd — now returns a real SSE stream (`connected` event followed by real `whiteboard_snapshot` fixture data). Re-ran the original network trace against `/emergency/settings`: the realtime-stream 403 is gone from the failure list (4 unrelated pre-existing issues remain, see below — not fixed this round, not conflated with this fix).
- **New leads found but NOT fixed this round** (recorded honestly, not guessed at): the same live trace also showed `POST /api/ai/node` returning 403 from a real browser session (but a direct curl with the same JWT and a minimal body passes all guards, reaching DTO validation instead — the real request must differ in some guard-relevant way not yet isolated), `GET /api/workspaces/context` returning 500 (a server error, not an auth rejection — potentially the highest-severity of the 4, worth checking first), `POST /api/crashes` returning 400, and `POST /api/emergency/operational-intelligence/evaluate` returning 403. Filed as new next-round candidates (see `CARE_DROID_MASTER_BACKLOG.md`'s Queue order section), not chased in this round to keep the SSE fix's blast radius clean and independently verifiable.
- **Commit when resolved**: (this commit)

### HEAL-072 (P1_HIGH, VALIDATED — 2 real root causes found and fixed; the suspected 3rd cause was investigated and disproven, closing the finding) — `/emergency/settings` took 40+ seconds to become usable

- **Severity**: P1_HIGH (a full route unusable for tens of seconds on every load)
- **Domain**: Frontend request architecture / performance (MB-J7 continuation; found while re-verifying the Settings-page lead flagged but not diagnosed in HEAL-069/070's round)

New permanent regression test `emergencyStore.workflowLogsCap.test.ts` proves both the `recordWorkflowAction` path (550 calls, asserts length stays ≤500) and the `hydrateFromApi`/`mergeWorkflowLogs` path (500 seeded + 1 incoming, asserts the cap holds AND that the newest entry survives the trim — the cap keeps the most RECENT entries, not an arbitrary prefix).
