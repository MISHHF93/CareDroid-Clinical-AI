## Correction (2026-07-29, same day, follow-up cycle)

The original §4.8 finding said `moe-router.service.ts` "calls the shared LLM client directly, bypassing `AIGatewayService`" and QW-1 proposed "route `moe-router.service.ts` through `AIGatewayService`" as a single-cycle fix. A follow-up cycle re-read the actual code before attempting that fix and found the claim was imprecise in a way that mattered: **`moe-router.service.ts` never calls an LLM at all** — it's a pure planner that returns an `ExpertRoutePlan` object; `UNIFIED_AI_MODEL` there is only ever used as a string value inside that plan. Within its one real caller (`chat.service.ts`), that plan already flows through `AIGatewayService.attachUnifiedNode()`/`logRoutingAudit()` correctly — there was nothing to "route through" the gateway.

The real, more significant bypass — confirmed by tracing every real usage of the shared `unifiedAIClient` — is in `backend/src/modules/ai/ai.service.ts`: 3 methods (`invokeLLM`, `generateStructuredJSON`, `invokeLLMWithTools`) call `unifiedAIClient.request()` directly, with **zero references to `AIGatewayService` anywhere in that 1500+ line file**. These back real, live, directly-HTTP-exposed endpoints (`POST /api/ai/query`, `/api/ai/structured`) and are also called internally by `IntentClassifierService`, `lab-interpreter.service.ts`, `drug-checker.service.ts`, and `parameter-collector.service.ts` — a wide, high-traffic surface with zero gateway-level audit logging today.

This is *not* a same-cycle quick win, corrected here rather than attempted rushed: `AIGatewayService.logRoutingAudit()` requires a full `ExpertRoutePlan`, which only `MoERouterService.createRoutePlan()` produces, which itself needs an `IntentClassification` — and `AIService` is called *from* `IntentClassifierService`, so naively adding intent classification inside `AIService` to build that plan risks a circular call pattern. §3 and §4.8 below reflect this corrected, precise finding; QW-1 has been withdrawn and replaced with QW-1′, reclassified as needing its own design pass alongside QW-4/QW-5.

## Second correction (2026-07-29, next cycle) — "zero audit logging" was itself wrong

Before designing QW-1′, a follow-up cycle checked whether `ai.service.ts`'s 3 direct-call methods really had "zero gateway-level audit logging," as the correction above claimed. They don't have gateway-level (`AIGatewayService`) logging — but the "zero audit logging" framing was wrong. All 3 methods (`invokeLLM`, `generateStructuredJSON`, `invokeLLMWithTools`) already call **both** a private `logQuery()` (persists a real, PHI-redacted `AIQuery` record with tokens/cost/latency/feature/conversation, records real usage metering via `SubscriptionsService`, and can trigger a human-review item) **and** `this.auditService.log({action: AuditAction.AI_QUERY, ...})` directly — on both success and failure paths, confirmed by direct read of all 3 methods. This is a real, substantial, independently-verified audit mechanism; it just isn't the `AIGatewayService` wrapper class specifically.

The real, narrower, precisely-scoped gap: `AIGatewayService.createRunEnvelope()` hardcodes `policy.requiresHumanReview: true` for every gateway-routed call (an unconditional, fail-safe default). `AIService`'s equivalent flag (`aiCommercialization.requiresHumanReview`, read by `createHumanReviewItemIfRequired()`) is derived from `context?.aiFoundation?.requiresHumanReview`, an *optional* caller-supplied value that defaults to `false` when absent. Checked all 5 real callers of `AIService`'s 3 direct-call methods (`ai.controller.ts`'s `/query`/`/structured` endpoints, `IntentClassifierService`, `lab-interpreter.service.ts`, `drug-checker.service.ts`, `parameter-collector.service.ts`) — **none of them set this flag**, meaning AI-generated content from every one of these paths, including two clinical-tool executors producing real lab-interpretation and drug-interaction output, never triggered the human-review workflow the chat/gateway path enforces unconditionally.

This *was* a safe, same-cycle, purely-additive fix — passing `{ aiFoundation: { requiresHumanReview: true } }` as `generateStructuredJSON`'s existing optional 4th argument doesn't touch `AIGatewayService`/`MoERouterService` or risk the circular-dependency concern above. **Fixed** in `lab-interpreter.service.ts` and `drug-checker.service.ts` this cycle, with new regression tests (both previously had zero test coverage) confirming red-before/green-after. `ai.controller.ts`'s direct endpoints, `IntentClassifierService`, and `parameter-collector.service.ts` still don't set the flag — left open, since whether those specific call sites should default to requiring human review is a narrower product/clinical-policy question than the mechanical lab/drug-checker fix, not decided unilaterally here. §3 and §4.8 updated accordingly.

## Third correction (2026-07-29, Cycle 235) — §4.14's "genuinely blocks real actions" overstatement, and the same claim on a live admin page

Scoping QW-4 (consolidate the two consent stores) before attempting it — the same "verify before implementing" pass that produced the two corrections above — surfaced a different, more consequential imprecision first, this time in §4.14 rather than §4.8. §4.14 said `evaluateGate()` "genuinely blocks real actions when classification/policy/consent data is missing." Tracing all 4 real production callers found that's true of none of them: `clinical-intelligence.service.ts` checks the decision but only to escalate to human review (draft generation proceeds regardless); `chat.service.ts` computes and logs the full decision but only branches on one unrelated reason; `tool-orchestrator.service.ts` discards the result entirely and doesn't even supply `phiAccessed`/`patientId`; `llm-security.module.ts`'s call sits behind a manual diagnostic endpoint, not a real AI action. See §4.14's own correction note for the full trace.

The same overstatement existed live, in the product itself, not just in this audit doc: `PlatformGovernanceWorkspace.tsx` — the real `/ai-governance`/`/security`/`/regulatory` admin dashboard — had a "Fail-closed behavior" card stating "Missing governance, consent, validation, classification, or audit controls block production action." Fixed this cycle to describe actual behavior (computed, logged, audited, always-`requiresHumanReview:true`; only ambient-scribe currently escalates a missing-control decision, and even that doesn't block). New regression test added. QW-4 itself (the store-consolidation question) remains open and unaffected — this correction only changes how urgently framed the *risk* around it should be, from "a real gate might be silently bypassable" to "an inert data-plumbing gap in a control most callers don't act on yet." See QW-6 (done).

## Scope note (non-negotiable)

**This document audits existing capability only.** It does not propose, size, scaffold, or begin building any of the 14 subsystems `research.md` describes, and it makes no claim of real HIPAA/PHIPA/Health-Canada regulatory compliance — it describes what code exists today, not a legal compliance determination (`research.md` itself says the final legal requirements need review by qualified privacy counsel). Where this document recommends a next step, it is limited to the **Quick wins** appendix (§3), which lists small, code-only fixes distinct from the 14-subsystem roadmap itself.

## Headline finding

This is **not** "14 things built from zero." Real, working, tested code already exists relevant to 11 of the 14 areas — it is fragmented across duplicate/parallel systems that don't share a write path, switched off by default behind one specific, well-documented architectural flag, or honestly self-reporting itself as demo/synthetic data. Only 3 areas (imaging, Canadian NACRS reporting, human-factors usability lab) are genuine greenfield with zero existing code. The single most useful thing this document does is separate "needs wiring/consolidation/enabling" from "needs building" — those are different kinds of work with different owners and different risk profiles, and conflating them would make every one of the 14 areas look like a from-scratch project when most aren't.

## 1. Classification key

Two independent axes. **Status** is `research.md`'s own literal ask, used as originally specified. **Pattern** is added here because the evidence below shows "duplicated" and "disconnected" alone can't distinguish four materially different situations — knowing *why* something is in the state it's in changes what fixing it actually costs.

| Status | Meaning |
|---|---|
| **production-ready** | Real, correct, exercised by real callers, no known gaps for its stated purpose |
| **partially implemented** | Real logic exists but is incomplete against its stated purpose |
| **mocked** | Runs, but returns fabricated/placeholder data by design |
| **disconnected** | Real code exists but nothing in the real app calls it |
| **duplicated** | Two or more implementations of overlapping scope |
| **deprecated** | Superseded, kept only for compatibility |
| **unsafe** | Reserved for a concrete failure scenario — a user or the system relies on a claim about this capability that is false, not merely "incomplete" |
| **missing** | Genuinely does not exist |

| Pattern | Meaning | Where it shows up below |
|---|---|---|
| **split-authority** | 2+ independently real, non-identical implementations, no single source of truth, no shared write path | Consent (§4), Clinical Knowledge Registry (§5) |
| **gated-by-design** | Real, more capable code exists but is off by default behind one specific, documented config flag | MPI Tier 2, part of Digital Twin (§2, §10) |
| **self-reporting-synthetic** | Wired and running, but its own response shape honestly declares the data fake | Interoperability, Digital Twin (§1, §10) |
| **narrowly-scoped** | Real, wired, tested governance exists, but only for a slice of what the stated purpose implies | Clinical Safety System, Regulatory Registry (§7, §14) |

## 4. Area detail

### 4.1 FHIR/HL7/interoperability — partially implemented, self-reporting-synthetic

Real code exists: `backend/src/modules/interoperability/integration-hub.service.ts` and `integration-automation-router.service.ts` do genuine field-mapping for FHIR `Patient`/`Observation`/`MedicationRequest`/`Encounter` resources, audit-logged via the real `AuditService`. But HL7 v2 handling is explicitly unimplemented — the methods are literally named `normalizeHl7AdtPlaceholder`/`normalizeHl7OruPlaceholder`. The controller (`InteroperabilityController.getSummary()`) self-reports `status: 'synthetic_ready'`, `connectionState: 'demo_unconfigured'`, `writebackAllowed: false`. `backend/src/services/fhir.service.ts` and `moh-fhir.service.ts` are ~10-40 line field-renaming stubs with no outbound HTTP calls; `backend/src/api/moh.routes.ts` is a `createPlaceholderRoute(...)`. No SMART on FHIR OAuth flow, no CDS Hooks discovery/prefetch protocol, no DICOMweb client exist anywhere in the repo.

### 4.2 Enterprise MPI / duplicate detection — partially implemented, two tiers

**Tier 1 (always-on):** deterministic weighted-field matching (`backend/src/modules/emergency-os/patient-duplicate-detection.ts`, frontend twin `src/utils/patientDuplicateDetection.ts`), genuinely wired into `SmartIntakeService.guardAgainstUnconfirmedDuplicate`, which throws a real `ConflictException` on an unconfirmed high-confidence match. No fuzzy/probabilistic matching, no merge/unmerge, no identity-correction workflow, no multi-identifier-domain support beyond flat `mrn`/`healthCard`/`phone` string fields.

**Tier 2 (materially more sophisticated):** `backend/src/services/mpi.service.ts` (Mongoose) supports multi-identifier-domain search (mrn/health_card/external_ehr/referral_source + phone/email/previousNames), plus `smart-intake.service.ts` implements session-based OCR/EMS evidence capture, staff field verification, match/link/create, `continueUnknown` (temporary "Unknown Male/Female" patient records), `reconcileUnknown` (later identity merge), biometric consent, and a per-session audit log — genuinely closer to what `research.md` describes.

**Gating, confirmed precisely:** Tier 2 is entirely off by default. `backend/src/main.ts`'s `registerEmergencyMongooseRuntime()` checks `config.database.enableMongooseEmergencyOs` (`ENABLE_MONGOOSE_EMERGENCY_OS` env var, default off per `backend/src/config/environment.config.ts`) and, if false, returns before mounting **the entire legacy Express route registry** (`registerAllRoutes`, mounted at both the default prefix and again at `/api/emergency`) *and* the EMS/ambulance WebSocket support — not just MPI. This is a documented, accepted architectural decision: **ADR-0002** ("Dual persistence — TypeORM + optional Mongoose") states it explicitly, including the real cost ("A load-bearing feature flag... easy to miss when debugging 'why are patient endpoints returning nothing' in a fresh environment") and that "no foreign-key integrity between the two stores" exists. This is `gated-by-design`, not an oversight — treat any other "disconnected"-looking legacy Express/Mongoose finding in this repo with the same lens before calling it dead code.

### 4.3 Structured/adaptive intake forms — missing

`src/components/QuickIntake.tsx` is plain `useState` fields. `src/pages/emergency/SmartIntake.tsx` renders a fixed field set sourced from `src/data/smartIntakeFixtures.ts`'s `SMART_INTAKE_DEMO.extractedFields` — an OCR-review UI over a named field set, not a declarative/branching form engine. No FHIR `Questionnaire`/`QuestionnaireResponse` concept, conditional-question logic, or versioned form-template system exists anywhere in `src/`.

### 4.4 Consent/privacy/provenance/break-glass — partially implemented, split-authority (break-glass false-assurance closed Cycle 232)

**Consent is split-authority.** `backend/src/modules/compliance/compliance.service.ts`'s `getConsentStatus()`/`updateConsent()` read/write real `UserProfile.consentDataProcessing`/`consentMarketingCommunications`/`consentThirdPartySharing`/`consentEssentialCookies` columns (Cycle 227 of the ongoing QA program fixed a real bug here: `getConsentStatus()` was reporting these from `user.emailVerified` instead of the real columns `updateConsent()` writes — fixed, but the fix only touched this one system's reads). Separately, `backend/src/modules/platform-governance/platform-governance.service.ts` has its own, independent `PlatformConsentRecord`/`upsertConsent`/`getConsent`, plus `PlatformPrivacyRequest` and `PlatformSourceProvenance` (the latter defaults `freshness: 'demo'`, seeded only with synthetic FHIR/HL7 fixtures) — wired to its own real, guarded controller (`platform-governance.controller.ts`). **Confirmed via a direct cross-import grep: zero references either direction between `compliance/` and `platform-governance/`** — genuinely two disconnected systems, not merely differently named views of the same data. The audit log backing both (`backend/src/modules/audit/audit.service.ts`) is real and substantial — SHA-256 hash-chained, tamper-evident, with a `phiAccessed` flag — but is not FHIR `Provenance`/`AuditEvent`-shaped (no coded who/what/why).

**Break-glass (remediated Cycle 232 — no longer false-assurance / `unsafe`).** Prior state: permission granted + docs claimed a working clinical override while no guard existed; `emergency-access.service.ts` is only 2FA backup-code recovery. **After QW-2:** `BREAK_GLASS_ACCESS` is not granted to any role (metadata RESERVED); every catalog role has `breakGlassAllowed: false`; architecture/service-catalog/glossary corrected. Clinical break-glass remains **not implemented** (honest gap), not mis-sold. See QW-2.

**Consent's real enforcement surface (Cycle 235).** `platform-governance.service.ts`'s `hasActiveConsent()` — the function `evaluateGate()` calls to decide `active_consent_missing` — is real and DB-backed, but the only real UI writer of a `PlatformConsentRecord` (`PlatformGovernanceWorkspace.tsx` / `platformGovernanceApi.ts`) is hardcoded to the literal patient id `'demo-patient'`; no live path writes a consent record for any real patient. In practice this means `hasActiveConsent(realPatientId, 'clinical_ai')` returns `false` for essentially every real patient, always. That sounds alarming in isolation, but see §4.14's correction: only 1 of `evaluateGate()`'s 4 real callers acts on a missing-consent decision at all, and it escalates to human review rather than blocking — so this isn't a live "AI acts without consent, undetected" gap, it's an inert data-plumbing gap in a control that (today) mostly doesn't do anything with the answer either way. Left as-is, cross-referenced from QW-4/QW-6 rather than fixed, since deciding whether `PlatformConsentRecord` should actually be written for real patients is bound up in QW-4's "which of the two consent stores is authoritative" design question.

### 4.5 Clinical Knowledge Artifact Registry — partially implemented, split-authority

`backend/src/modules/clinical/protocol.service.ts` + `protocol.entity.ts` is a real, DB-backed CRUD registry — but a flat `{name, category, description, steps: string[]}` table with no versioning, governance workflow, or execution semantics. Separately, `src/clinical-calculators/` (`qsofa.ts`, `heart.ts`, `news2.ts`, `nihss.ts`, `gcs.ts`, `wellsPe.ts`, and others feeding `CLINICAL_CALCULATOR_REGISTRY`) is a real, clinically-correct, hardcoded-in-TypeScript registry — each formula is inline code, not data-driven or independently versioned. No `PlanDefinition`/`ActivityDefinition`/CQL/FHIRPath concept, and no single governed source of truth across the two.

### 4.6 CDS Hooks / workflow-triggered decision support — missing

`src/engine/journeyEngine.ts` is confirmed to be a pure patient-state finite-state machine (`VALID_TRANSITIONS` between Arrival→Registration→Triage→...→Discharge) — no hook/prefetch/service-definition concept at all. `backend/src/modules/emergency-os/clinical-decision-support.service.ts` is the closest named artifact, but it's an in-memory array (capped at 500 entries, no DB persistence) that stores calculator results and copilot-interaction logs *after the fact* — it does not trigger on events like `patient-arrived` or `critical-result-received`. (Its own `envelope()` helper *can* mark a response `status: 'placeholder'` when gaps remain, but every call site in the file currently passes an empty gap list, so in practice every response self-reports `'active'` today — the mechanism exists but isn't presently triggered; stated precisely rather than implying live responses come back flagged incomplete.) No hook registry, prefetch template, or event-subscription mechanism exists anywhere.

### 4.7 Clinical Safety Management System — partially implemented, narrowly-scoped to AI

No hazard log or safety case exists anywhere in the repo (confirmed by full-text search; the only hits are `research.md` itself). But real, wired AI-specific governance does exist: `lib/ai/modelRegistry.ts` reads `data/model-registry/entries/*.json` — confirmed exactly **5** real seeded model entries (`mdl-caredroid-heuristic-node-v1`, `mdl-claude-sonnet-4-6-v1`, `mdl-local-deterministic-v1`, `mdl-offline-eval-harness-v1`, `mdl-unified-ai-node-v1`), each with a purpose/prohibited-uses/limitations schema (`data/model-registry/schema/model-entry.schema.json`), documented in `docs/ai/MODEL_REGISTRY_v1.md`. `lib/ai/productionMonitoring.ts` is a real event recorder (egress success/failure, kill-switch, PHI redaction), called from `lib/ai/providers/egress.ts`. `docs/ai/CLINICIAN_REVIEW_CHECKLIST_v1.md` exists. All of this is genuine — but narrowly scoped to AI/model risk specifically, not the platform's broader non-AI clinical risk (e.g. a miscalibrated triage-priority rule with no AI involved has no equivalent governance artifact).

### 4.8 AI Execution Gateway — partially implemented, confirmed bypass (corrected finding)

`AIGatewayService` (`backend/src/modules/ai-gateway/ai-gateway.service.ts`) is real but narrow — exactly 4 methods (`createRunEnvelope`, `attachUnifiedNode`, `toMetadata`, `logRoutingAudit`), none of which invoke an LLM themselves; it's an envelope/audit-metadata helper, not a true execution chokepoint that owns the call. It's correctly used by its one real caller, `backend/src/modules/chat/chat.service.ts`, which builds an envelope, attaches the intent-classification snapshot, and logs a routing audit entry *before* making its own direct `unifiedAIClient.request()` call later in the same method.

`backend/src/modules/moe-router/moe-router.service.ts` was originally flagged here as bypassing the gateway — checked directly and that's imprecise: it never calls an LLM at all; it's a pure planner returning an `ExpertRoutePlan`, and `chat.service.ts` already feeds that plan through `AIGatewayService` correctly. Nothing to fix there (see the correction note above).

The real bypass: `backend/src/modules/ai/ai.service.ts` — confirmed via `grep` across the whole file — has **zero references to `AIGatewayService`/`aiGateway` anywhere**, and makes 3 independent direct `unifiedAIClient.request()` calls (`invokeLLM`, `generateStructuredJSON`, `invokeLLMWithTools`). These back real, live endpoints (`POST /api/ai/query`, `POST /api/ai/structured`, confirmed via `ai.controller.ts`) and are also called internally by `IntentClassifierService`, `lab-interpreter.service.ts`, `drug-checker.service.ts`, and `parameter-collector.service.ts`.

**This traffic is not unaudited** — a claim in an earlier version of this section that a follow-up cycle checked and corrected. All 3 methods call a private `logQuery()` (real, PHI-redacted `AIQuery` persistence with token/cost/latency tracking and real usage metering via `SubscriptionsService`) and `this.auditService.log(...)` directly, on both success and failure paths. What's genuinely missing, and gateway-level envelope creation would provide automatically, is *centralized, non-optional PHI/policy classification*: `AIGatewayService.createRunEnvelope()` hardcodes `requiresHumanReview: true` unconditionally, while `AIService`'s equivalent flag is optional and caller-supplied, defaulting to `false`. Checked all 5 real callers — none set it. **Fixed** for 2 of them in Cycle 230 (`lab-interpreter.service.ts`, `drug-checker.service.ts`). **Cycle 233** also fixed `ai.controller.ts` `POST /ai/query` and `POST /ai/structured` (Swagger-described clinical assistance/output) so they always inject `aiFoundation.requiresHumanReview: true`, matching gateway fail-safe — even if a client sends `false`. Still **not** forced on `IntentClassifierService` (routing-only, not clinician-facing output) or `parameter-collector.service.ts` (intermediate tool-arg extraction; flooding review for every missing param would be noise) — deliberate product scope, not oversight.

Properly integrating *all* of `AIService` with `AIGatewayService` itself (not just the `requiresHumanReview` flag) isn't mechanical: `logRoutingAudit()` requires a full `ExpertRoutePlan` (only `MoERouterService.createRoutePlan()` produces one), which itself needs an `IntentClassification` — and since `AIService` is itself called *from* `IntentClassifierService`, naively classifying intent inside `AIService` to build that plan risks a circular call. See QW-1′ in §3.

The AI evaluation lab is real: `backend/src/modules/evaluation/` (service + spec + controller), `docs/ai/AI_EVAL_HARNESS_v1.md`, an `npm run ai:eval:gate` script referenced in the clinician checklist — but only chat-path traffic is actually gated and audited end-to-end today.

### 4.9 OCR Document Intelligence — partially implemented, most mature of the 14 areas

`backend/src/modules/emergency-os/ocr-providers.ts` has a genuine `TesseractOcrProvider` using real `tesseract.js` `worker.recognize()` against decoded image buffers, with a `MockOcrProvider` available for dev/test (selected via `OCR_PROVIDER` env var; defaults to real Tesseract). `ocr-intake.service.ts` + `ocr-intake.types.ts` implement: document-type classification against exactly **10** real artifact types defined in `src/config/intakeArtifactRegistry.ts`'s `IntakeArtifactId` (`government_id`, `health_card`, `drivers_license`, `passport`, `insurance_card`, `medication_list`, `allergy_list`, `referral_letter`, `clinic_notes`, `discharge_summary`), per-field confidence scoring, a real human-review state machine (`pending`/`accepted`/`edited`/`rejected`), a full per-job audit log (`OcrJobAuditEntry`), and a health/drift signal (`OcrHealthSnapshot`, tracking failure rate into `healthy`/`degraded`/`down`). ### 4.14 Regulatory boundary / Feature Intended-Use Registry — partially implemented, narrowly-scoped

`backend/src/modules/platform-governance/entities/platform-governance.entities.ts`'s `PlatformRegulatoryClassification` (jurisdiction, classification, riskLevel, `intendedUse`, `excludedUses`, `requiresHumanReview`) is real and DB-backed. Its `evaluateGate()` computes a real, evidenced `allowed`/`reasons` decision from classification/policy/consent data and — checked directly, not assumed — is actually called from **6 real sites**: `chat.service.ts`, `clinical-intelligence.service.ts`, `governance.controller.ts`, `platform-governance.controller.ts`, `llm-security.module.ts`, and `tool-orchestrator.service.ts`. This is real, load-bearing governance scaffolding — but it's seeded only with synthetic FHIR/HL7 fixtures, not a registry that classifies the app's actual ~100+ real features one by one. `src/pages/legal/TermsOfService.tsx` has a one-line "Not a Medical Device" disclaimer — legal boilerplate, not a registry entry. For context, this same entitlement/gating machinery has had genuine live bugs before (see §5, Cycle 221) — real code, exercised, occasionally wrong, not untested.

**Correction (Cycle 235):** this section originally said `evaluateGate()` "genuinely blocks real actions when classification/policy/consent data is missing" — checked precisely and that overstates it. Every response unconditionally sets `requiresHumanReview: true` and is logged/audited regardless of `allowed`, which is genuinely real. But tracing what each of the 4 real *production* callers (excluding the 2 controllers, which just pass the decision through as an API response) actually does with `allowed`/`reasons` found only **1 of 4 acts on it**: `clinical-intelligence.service.ts`'s ambient-scribe flow checks `!allowed`, but only to add a review-queue item (`severity: allowed ? 'medium' : 'high'`) — draft generation proceeds either way. `chat.service.ts` computes the full decision and only branches on one specific reason (`prompt_security_review_required`); `active_consent_missing`/`active_regulatory_classification_missing`/`active_governance_policy_missing` are logged and returned as response metadata but never checked. `tool-orchestrator.service.ts` `await`s the call and discards the result entirely — and passes neither `phiAccessed` nor `patientId`, so consent is structurally never even evaluated there. `llm-security.module.ts`'s call is behind a manual `POST /evaluate` diagnostic endpoint (`Permission.VIEW_AI_SECURITY`), not wired to any real AI action. Net effect: this is real, audited, logged decisioning wired into genuine call sites — "genuinely blocks" was true of none of them; "genuinely escalates to human review" is true of exactly one. Whether more of these should hard-block is the same class of product/clinical-safety decision this document has consistently declined to make unilaterally (see QW-1′/QW-4/QW-5) — not fixed here. The one concrete, safe fix this correction did make: `PlatformGovernanceWorkspace.tsx` (the real, rendered `/ai-governance`/`/security`/`/regulatory` admin dashboard) had a "Fail-closed behavior" card claiming, in the product's own words, that "missing governance, consent, validation, classification, or audit controls block production action" — a live, user-facing instance of the same overstatement. Corrected to describe actual behavior. See QW-6.
